# Artwork approval implementation and operating procedure

Prepared November 5, 2026. **Not deployed. The migration has not been applied to the hosted database.** Terms remain a draft for business/legal review. The existing October 20 preview is the canonical design, recovered from source commit `66960e271d7fb34b6c35ae9cb5533e94bfbb90c9`. Its appearance, per-design decisions, and revision history are preserved; real records use the website API and database instead of browser-local storage.

## Customer and staff experience

- Manage approvals in the existing `/admin` Orders dashboard, using its Artwork Approvals tab or an order's Artwork button. The old `/admin/approvals` address redirects there. Existing admin sign-in protects every staff API call.
- Website and manual/offline orders can contain up to 200 designs. Each design has independent proof revisions, product, quantity, width/height/units, material, finish, special-printing instructions and customer notes.
- The customer opens `/approve#<confidential-token>`. There is no public approval directory or navigation link. The route is marked noindex and API responses are no-store; the fragment is not sent as an HTTP URL or referrer. Customer requests carry the token in a POST body. A random 256-bit bearer token and the issued-to email provide access/attribution; this is not email verification or MFA.
- One job retains one link across additional designs and revisions. Tokens are looked up by SHA-256. An AES-256-GCM sealed copy lets authenticated staff recopy the same link. It uses a server-only key derived from the existing JWT secret; rotating that secret requires replacing affected links before they can be recopied. Raw tokens and sealed copies never appear in the customer record projection.
- Links expire after 30 days. Staff can replace/renew a link, invalidating its predecessor without deleting approvals, or permanently close an active job. A fulfilled order cannot be closed through this control; its records remain and links expire normally.
- Customers review each current design and choose Approve, Request changes or Decide later. One submission can combine different responses. A pending design left for later stays on hold.
- Approval requires three initially unchecked statements, a typed full name and the issued-to email. The signature-intent text appears beside Submit Responses. The saved statements and complete agreement come from that proof's frozen terms snapshot. Changing the selection resets all consents. Designs with different terms versions must be approved in separate submissions.
- Photo/promotion permission is a separate, optional unchecked box. It affects only the exact approved designs/versions in that submission. Restrictions such as an embargo date are retained only with an affirmative opt-in. Change requests and future revisions receive no inherited permission.
- The entire selected batch is validated and committed atomically. A stale design, file hash, manifest version, terms version, wrong job or recipient, duplicate decision, or invalid change request rejects the batch. After a network interruption, refresh to see whether the response was recorded before retrying. Already-recorded responses are not overwritten.
- Each receipt retains the exact proof, SHA-256, design/revision, specifications, terms version/full text, statements, signer-supplied name/email/business, server UTC time, submission ID, selected approved proof IDs, requested changes and promotional choice/restrictions. Internal reviewer notes remain staff-only. Receipts can be printed or saved as PDF; an order JSON export embeds the proof files and history (100 MB export limit).

## Staff procedure

1. Identify the customer and authorized approver. Select an existing website order or create a manual job. Include complete specifications and every relevant page/item in each final proof.
2. Review the artwork and identified rights concerns before sending it. Retain relevant written permissions/licenses and refer to that evidence in internal review notes. Customer confirmation does not establish a license or resolve a rights concern.
3. Upload the exact PDF, PNG, JPEG or WebP proof, up to 2 MB per file. Record reviewer, review notes and the affirmative internal-review check. Uploads go to a private bucket; file hashes are calculated server-side. Specification-only revisions may copy the same exact file to a new retained proof object.
4. Copy the confidential customer link and send it manually through the usual customer channel. This implementation does not send approval invitations automatically. Do not publish or send a link to an unintended recipient. Replace the link if disclosure is suspected.
5. Refresh the job to see responses. Hold the entire linked website order until **every current design** is approved. Database controls block production, quality control, shipping and completion without those approvals and a matching order snapshot. Payment, silence and checkout are not proof approvals.
6. Revise only the affected design when artwork or specifications change. Its new proof requires fresh approval; earlier signed records and other designs' approvals remain. An order in production or QC returns to `processing` when a design or revision is issued. Changes to linked order items, notes or customer email require fresh matching proofs.
7. Before operating the printer, compare the actual production file/specifications to the current approvals and confirm payment and internal review. The application cannot stop a physical printer or external production system. Staff must enforce holds for manual/offline jobs.
8. Retain exact proofs, responses, evidence references and related correspondence. Link expiry does not delete records. Close jobs rather than deleting evidence. Use a new order/job for a reprint after shipping, delivery, completion or cancellation. Set retention and backup procedures with the insurer/legal adviser before any purge.

It does not authorize final production. The original four artwork-review sections supplement those terms at final approval.

## Verification and practical limits

- `npm test`: 44 policy, original-workflow, PostgreSQL, API and post-review authorization tests. The actual Next route handlers, server validation, encryption, record projection and SQL run against local PostgreSQL (PGlite); only the Supabase network/storage transport is replaced. Post-review tests mock outbound HTTP and never contact the live automation.
- `npm run build`: production build passed November 5. `npx tsc --noEmit` also passed. Browser QA confirmed the original layout, mixed decisions, required checks, consent resets, promotional restrictions, independent revision/history, a customer link's missing-token state, and admin sign-in protection. Authenticated staff browser flow and hosted end-to-end verification remain pending access/deployment.
- The `/approval-preview` sample uses the same renderer with an in-memory test adapter. It is available locally and on protected Vercel Preview deployments, creates no real customer records/emails, resets on reload, and returns 404 on the live Production deployment. The review branch uses branch-specific dummy database, authentication, email and webhook settings rather than live integrations. The original hosted demo is unchanged.
- Public/customer DB roles cannot read/write approval tables or execute mutations. A restrictive storage policy excludes this private bucket even when older broad permissive policies exist. Proof viewing uses five-minute signed file URLs; refresh the page if a download expires. The existing ordinary design-upload bucket is outside this change.
- Signed evidence cannot be edited/deleted through this application. A privileged database/storage owner can still alter data or disable protections. Controlled owner access, backups and an agreed retention process remain necessary; there is no external notarization service.
- Lock order is linked order → job → design → proof. Local tests cover behavior and representative roles; they do not replace hosted adviser checks or multi-connection load/concurrency testing.
- This is not a full security audit of every legacy website feature. The all-orders endpoint is now admin-only because this management flow consumes it.
- Prefer a forward fix if rollout must pause. Retain all proof data and files. Do not casually drop the tables/bucket or disable the production gate. Reverting only the app restores the old checkout behavior and requires an explicit operating hold.
